 	%-------------------------------------------------------------------------------
 	\section{Paper Summary}
 	%-------------------------------------------------------------------------------
 	\subsection{Context}
 	%1. Context of the work (“Why”?)
 	%What is the problem? 
 	Minotaur is a superoptimizer that tries to identify missed optimization opportunities by the LLVM compiler by slicing generated IR and trying to synthesize new faster code.
	Its synthesizer creates improved machine code, generating and comparing equivalent but cheaper instruction sequences.
	To guarantee correctness of the optimization, Alive2 was extended to formally verify the generated code.
	Additionally, to reduce computation overhead, Minotaur also caches discovered transformations for reuse them in future compilations.
 	
 	%Why is it important or interesting? 
 	The use case of Minotaur is to further optimize already heavily optimized code from a compiler which still often contain suboptimal code segments, particularly for SIMD operations.
	The authors showed that even LLVM's advanced autovectorizer produced redundant or inefficient SIMD instructions.
	For those missed opportunities, Minotaur can correct these suboptimal instruction sequences by replacing them with improved machine code during the compilation.
	Some of those optimizations could be generalized and added to LLVM.
	Hence, the authors enabled higher performing and additionally formally verified machine code generation through the use of Minotaur.
 	
 	%What is the state-of-the-art? What is the “research gap”? 
 	Before Minotaur, several superoptimizer already existed that search through the code, be it assembly or LLVM IR, for more efficient sequences instead of performing set rewriting rules like traditional compilers.
	Common examples include Souper -- with focus on scalar integer optimizations and which also uses LLVM IR -- and STOKE, which uses stochastic search for faster x86 code blocks.
	However, those tools only addressed part of the problem.
	Souper~\cite{DBLP:souper} detects only improvements for integer operations, but not for floating-point or SIMD instructions.
	STOKE's~\cite{DBLP:stoke} improvements include complex optimizations, but the tool relies on randomized testing and not formal verifications for its transformations. % I think this changed in 2019 with https://doi.org/10.1145/3314221.3314601
	Therefore, the combined challenge of performing complex vector or floating point optimizations, formally verifying the transformation and integrating those capabilities into production compilers remained unsolved, until Minotaur. 
 	
 	%Why is it difficult? Or what are the challenges?
 	Designing a efficient and high performing superoptimizer included several challenges.
	First, the search space of replacement options for a suboptimal code sequence is enormous, making an exhaustive search for the optimal choice computationally expensive.
	Second, the semantic formal and not random equivalency check adds further overhead -- especially for hard to verify SIMD and floating point operations.
	Minotaur relies on SMT solvers for equivalency checks between the original code and the proposed optimization, but these solvers often struggle with large complex expressions.
	At the same time a sufficiently large number of lines of code is needed to provide enough context to be able to find improvement options in the first place.
	Furthermore, since Minotaur aims for low level, hardware aware optimizations, the authors used detailed information about pipelines and cache effects to accurately model the performance of optimizations.
	These difficulties of realizing high performance without too much computational cost, required a multiple stages process. 
 	
 	\subsection{Contributions}
 	%2. Contributions of the work (“How”?)
 	%What is the proposed solution? 
 	%How it works at a high-level?
 	%At high level, the authors decomposed the optimization process into three main stages. 
 	Because today's SMT solvers cannot optimize entire LLVM functions, Minotaur instead optimizes each instruction individually.
	It therefore breaks the LLVM function in SSA form down into cuts, which are small loop-free subsets of the the instruction's dependencies, to capture where the data used by the instruction came from.
	The size of the cut hereby influences the optimization, as too small cuts contain not enough context to determine a better code sequence, while too large cuts increase the solvers computation time dramatically.
	Minotaur's cut extraction is noticeably better than previous ones since it is able to handle memory operations, vector operations and floating-point operations.
	Through an empirical study the authors selected the cut size of four as it provides a good balance between finding most optimization while still running in an acceptable amount of time.
	For each cut, a set of potential alternatives which are faster are synthesized.
	These improvements are then verified with Alive2, which the authors extended to support SIMD operations.
	Lastly, for each optimization its speedup is estimated using a more accurate model (LLVM MCA) and its original and transformed code is cached for reuse in future compilations. 
 	

 	%What are the key insights? 
 	%Or what are the novel aspects? 
 	To measure how Minotaur's optimizations influence the overall performance of larger software projects, the authors benchmarked Minotaur on the SPEC CPU 2017, GMP and libYUV on Intel and AMD hardware with LLVM 18 compiled with -O3 and -march=native.
	They determined a maximum speedup of 1 - 7 percent, where integer SIMD fragments made up 75 percent of the discovered rewrites.
	When the compilation is performed with an empty cache, Minotaur increased compile times significantly.
	With a filled cache, however, only an additional 3 percent of computation time was needed.
	Overall, the authors found 15 simple and general floating-point and vector optimizations, which they then reported to the LLVM project.

 	\section{Artifact Evaluation Results}
 	%-------------------------------------------------------------------------------

	First, it has to be mentioned that the paper did not provide a exact git commit hash for the minotaur version that was used by the authors to run their benchmarks.
	Since we could not determine which version was used it was decided to evaluate the most up to date version of minotaur\footnote{\url{https://github.com/KiSchulz/minotaur/tree/8ae5395286ba40fa29c16a0229fd3d6e9795d4cd}}.
	One important difference between the most recent version and the version referenced by the authors in the paper is that the version in the paper relied on LLVM 18 whereas the newest version uses LLVM 20.

	Second, the most up to date version of minotaur, as of writing, does not work out of the box.
	For it to not immediately crash on startup, the order in which the libraries are linked by minotaur had to be changed.
	This changes the order in which the offending dynamic libraries are loaded when the program is started and thereby fixing the issue of undefined symbols.

	Third, minotaur uses alive2's LLVM interpreter which is listed as highly experimental \footnote{\url{https://github.com/AliveToolkit/alive2/tree/master?tab=readme-ov-file\#running-the-standalone-llvm-execution-tool-alive-exec}} and caused multiple crashes.
	Some of which where not reliably reproducible and could therefore not be debugged.
	In order to mitigate this, the compiler was run multiple times or problematic source files were filtered.
	More about that when the setup for libyuv is discussed.
	Some other bugs could be fixed.

	Fourth, the caching of minotaur seems to not fully work in the last release, as compiling a source file multiple consecutive times still leads to cache misses.
	This might be caused differing inputs from LLVM's side.
	Nevertheless it produces different binaries than running LLVM without the minotaur plugin.

	After those issues were addressed, as far as possible, a run could be attempted.
	Everything was compiled with the -O3 and -march=native flags as described in the paper.
	We benchmarked libgmp-6.2.1, as the paper did, and a fitting version of libyuv, which is able to build with LLVM 20.
	All runs were performed with the same parameters as the paper described i.e. a depth bound of 4, total synthesizes time of 5 minutes and a 1 minute timeout for individual smt queries.
	The benchmarks were build and run on an AMD Ryzen 9 5900X whereas the authors used an AMD Ryzen 9 5950X.
	The former has 12 cores running at up to 4.8 GHz whereas the latter has 16 cores running at up to 4.9 GHz.


	libgmp:
	According to the paper the build with an empty cache took 440 minutes for libgmp.
	Our build took approximately 1020 minutes while using a partly dirty cache from previous attempts.
	It seems unlikely that the difference in build times are caused by the hardware.
	This difference in compile time could be caused by the authors using the offline mode of minotaur which we intentionally did not use since as discussed earlier the cache did not work as expected.

	After finishing the build of libgmp the provided tests were run.
	When building with vanilla LLVM all tests passed without any issue.
	In contrast, using minotaur at least two tests failed namely t-root and t-perfpow.
	This indicates some correctness bug in alive2 or in how minotaur uses alive2.
	Later more of that is discussed.

	Ignoring the failing tests and the other issues, we could not see any speedup when running the benchmark using minotaur \ref{our_libgmp}.
	There could be multiple reasons for this.
	One could be that any of the previous issues which we were not able to solve yet caused this.
	Or, alternatively that most of the relevant optimization found by minotaur in LLVM 18 are now already present in LLVM 20.
	This is not entirely implausible since the authors were able to get some of the found optimizations merged into LLVM.
	The high variance between the single benchmarks could either stem from minotaur optimizations or be caused by the system executing the benchmark.
	Nevertheless the overall results did not change significantly between the benchmark runs.

	libyuv:
	In order to be able to even build libyuv and to not run into constant crashes during the compilation phase, its third party dependencies were compiled without minotaur.
	This would probably not have influenced the results to much since those dependencies seemed to be used mainly for auxiliary functionality.
	Due to us not compiling the third party dependencies comparing compile times makes little sense since the authors seemed to compile all sources using minotaur judging by their compile time.
	But in the end we were not able to run the benchmark suite of libyuv, which doubles as its test suite, since it was failing the tests using minotaur.
	Similar to the results for libgmp the vanilla LLVM build passed the tests with no issues.

	These results prompted us to investigate further.
	We decided to try to reproduce some of the optimizations for short LLVM IR code snippets listed in the paper. Since the original C source code is not provided, we attempted to optimize the IR directly. However, we observed through different experiments that starting from LLVM IR rather than from the C code often leads to different optimization results, which could partially explain the poor results obtained.

	In 5 of the 9 snippets tested, minotaur failed to produce any optimization. Only in the case of example 3 minotaur successfully generated optimized code that even then differed slightly from the one presented in the paper. In the case of example 6, the standard LLVM was able to produce the expected optimization but minotaur failed to do so. Finally, in examples 7 and 8 minotaur produced new code which featured more instructions than the original, non-optimized code. In example 7, however, standard LLVM also produced an optimization but it was different from the one presented in the paper.

	We also attempted to reproduce optimizations reported by the paper authors in LLVM's GitHub issues. In most cases tested \footnote{https://github.com/llvm/llvm-project/issues/88168} \footnote{https://github.com/llvm/llvm-project/issues/86079} \footnote{https://github.com/llvm/llvm-project/issues/86068} \footnote{https://github.com/llvm/llvm-project/issues/86063} \footnote{https://github.com/llvm/llvm-project/issues/86061} both minotaur and LLVM were able to produce the expected optimizations. However, in one case \footnote{https://github.com/llvm/llvm-project/issues/88030} minotaur failed to reproduce the expected optimization. Only in one of the tested issues \footnote{https://github.com/llvm/llvm-project/issues/118114} minotaur produced an optimization that LLVM could not by eliminating an entire function.

 	\section{Research Ideas}
 	%-------------------------------------------------------------------------------
 	
	\subsection{Improved caching}

	As previously discussed caching, which should be a key mechanism for reducing compile time, does not appear to operate very effectively in the current version of Minotaur. A plausible reason is that cached rewrites are keyed on the literal structure of extracted cuts, causing near misses on semantically equivalent cuts. A possible approach to this is the introduction of a canonicalization layer so that identical computations map to the same key. This could be implemented through the normalization of SSA identifiers, sorting of operands in commutative instructions and the standardization of other elements like vector masks. The impact of these changes could be evaluated by measuring improvements in cache hit rates, reduction of solver timeouts and compilation times, as well as by checking whether more rewrites are successfully applied across different programs.

	\subsection{Dynamic Cutting Depth using Profile Guided Optimization}
	%Dynamic cutting depth depending on benchmark data i.e. sampling profiler (profile guided optimization).

	% What is the problem: long compile times
	% Why is it important: compiles already for hours for small projects which usually take seconds to build.
	One major down side of minotaur at the moment is its long compile times.
	Even for small projects, which usually compile within seconds, it can take thousands of times longer, making it hours or even days.
	Improving on compile time could enable a more practical use of minotaur.
	% Why is it difficult or what are the challenges: There are multiple ways to go about this either improve the proving speed, improve function synthesis, finding a dynamic depth bound as suggested by the paper
	The main challenge is how to save on time while compiling and to not lose the benefits of minotaur i.e. runtime performance improvements.

	% What is the proposed idea: using perf to find hot code sections and spend time on the most importent parts
	% How will it work: first build the project with llvm, second run a benchmark with perf, third build it again with perf data and minotaur which then dynamically determines the depth bound
	To achieve this one could try, as the paper suggested, to dynamically set the cutting depth.
	Determining the cutting depth for each cut is hard since one would have to know how important a pice of code is to the overall runtime performance.
	One simple way of doing this would be to first build the given code without minotaur and then benchmark it while gathering data with a profiler.
	This profiling data could then be used in a second compilation of the code using minotaur to determine the cutting depth in minotaur dynamically during compilation.
	In theory two goals could be achieved, namely reducing total compile time, by not spending time on unimportant code like code that is only ever executed once, and second, it could also enable minotaur to spend more time on important code which actually impacts performance.
	% How would you measure and evaluate the idea: measure compile time and runtime between minotaur without perf data and with perf data
	Changes in compile time between the papers version of minotaur and the augmented version would be the first important metric.
	But this is obviously not enough, one also has to measure the runtime in order to determine if the proposal delivered any benefits.
	% What would be the potential impact: faster compile times while having similar or better runtime performance
	Ideally the suggestion would improve compile times by not optimizing non critical code while keeping or maybe improving runtime of the code.

	\subsection{Arm Support}
	% What is the problem: currently only x86 is supported
	Currently minotaur only supports x86 architectures. While it contains a large amount of x86, intrinsics it still uses LLVM IR which is platform-agnostic.
	% What is the proposed idea: add ARM support
	When considering ARM LLVM support for NEON is more robust and more similar to x86 used in minotaur.
	Adding ARM support would entail implementing ca. 100 intrinsics (the x86 version of minotaur uses ~ 165), of which many are type duplicates, i.e. 32 bit and 64 bit variants.
	While this seems feasible, it would also require modifying the register allocator and verifying the formal verification in alive2 to support ARM specific instructions.
	Furthermore, optimizations found on x86 might not be applicable to ARM and vice versa, so a new cost model would be needed.
	As a result this seems to be a significant engineering effort, which also requires advanced ARM benchmarking to determine which operations
	are faster on ARM hardware.
	% How would you measure and evaluate the idea: benchmark on ARM hardware
	Benchmarks similar to the ones used in the paper could be used to evaluate the performance of minotaur on ARM hardware.
	% What would be the potential impact: wider applicability
	Adding ARM support would increase the applicability of minotaur and allow it to work on more hardware platforms.

	\subsection{Developer Tools}
	% What is the problem: minotaur does not provide a well-thought out user experience
	Currently minotaur is largely a black box. While you can log the transformations via cache-dump of the redis cache, this is no very user-friendly format.
	% What is the proposed idea: better introspection tools
	An improvement would be better introspection tools to enhance minotaur as a research tool specifically. 
	The cache can be made queryable and interactive via a web interface. Instead of raw LLVM IR one could display the rules used in the synthesis.
	This goes hand in hand with statistics gathering about which cuts produce the most optimizations, which optimizations are most common and which optimizations produce the highest speedup
	in the benchmarks. For example Graphviz could be used to visualize the cuts and their optimizations and a snippet view could show code before and after optimizations.
	% How would you measure and evaluate the idea: user study
	One can let a third party developer use minotaur without the tools and with the tools and gather feedback.
	% What would be the potential impact: easier to use for researchers
	This would make minotaur and its optimization more accessible to researchers and make it less cumbersome to use.
