 	\section{Introduction}
	% What is the problem?
	% Why is it important or interesting?
	Minotaur \cite{liu24:minotaur} is a superoptimizer, that after computing optimizations, caches them in a database.
	For this purpose, it uses original code segments as keys to find rewrites/optimizations, which are stored as values.
	The intention behind the caching is to speedup the substantial runtimes of Minotaur for future compilations of the same or similar programs.
	Minotaur's compile times, with a cold cache, can easily be hundreds of times slower than with regular LLVM \cite{liu24:minotaur}.
	
	% What is the state-of-the-art? What is the research-gap?
	% Current state in Minotuar
	Currently, Minotaur uses extracted LLVM IR code segments directly as cache keys, storing them alongside rewrites in Minotaur's own IR as values.
	An example for a key-value pair is shown in figure \ref{fig:kv}.

	\input{kv_example.tex}

	This approach can lead to cache misses because semantically equivalent code segments may have different signatures.
	For example, if a cached segment has unused arguments while the current segment does not, the cache lookup fails and triggers a costly recomputation.
	% To mitigate this we extended Minotaur \cite{liu24:minotaur} to support key canonicalization through multiple steps.

	% Why is it difficult? What are the challenges?
	To avoid this issue we attempt to increase the number of cache hits.
	This leads to reduced compile times of Minotaur even when starting from a cold cache.
	The main challenge is to maintain correctness of the cached optimizations.

	\section{Research Proposal}
	% What is the proposed solution?
	% How it works at a high-level?

	To address the issue of near cache misses, our solution introduces an additional preprocessing step before a key is used for a cache lookup.
	It performs multiple code transformations to map semantically equivalent code to a "canonical" representation.

	% What are the key insights?
	% What are novel aspects?
	The idea is that this leads to fewer cache entries, an increased cache hit rate and fewer slow optimization searches by Minotaur.
	For large enough projects this can already take effect during an initial build, even when starting with an empty cache and thereby reduce the compile time.

	\section{Canonicalization}
	% TODO explain what is meant by equivalence or refer to a later text position
	To motivate the idea of canonicalization we start by defining the set of all valid LLVM IR snippets and call it the key space.
	The key space consists of equivalence classes of semantically equivalent keys.
	We call a set that contains one representative of each equivalence class a canonical key space.
	An ideal transformation would map each input LLVM IR snippet to its representative in a canonical key space.
	Using such a transformation would enable reaching the optimal cache hit rate and avoid unnecessary expensive optimization searches by Minotaur, since there would be no cache misses anymore where an equivalent equivalent snippet has already been processed.

	% TODO: think about how hard this is i.e. np-hard or not even computable
	Finding such a transformation is hard, therefore we attempted to only shrink the size of each equivalence class. % , resulting in a increased hit probability for each cache query.
	For this relaxation to work, each equivalence class has to be finite.
	This is because the probability that two randomly selected keys from the same equivalence class are identical depends on the size of that class.
	Because Minotaur only generates slices up to a fixed depth, it is possible to achieve finite equivalence classes with a transformation normalizing the names in a code snippet.

	% How did you design and implement the system?
	Our extension is placed as a pre- and postprocessing step around Minotaur's inference step.
	We intercept the LLVM IR produced by the slicer and perform transformations on it to produce a modified version of the input, which is then forwarded to the inference step.
	In the following this set of transformations is called canonicalization.
	After the inference step is done and returns a rewrite in Minotaur's own IR, another set of transformations on the rewrite is performed.
	This process is called de-canonicalization from now on.
	Figure \ref{fig:architecture} gives an overview of how our extension integrates into Minotuar.	

	% TODO add a figure ilustrating our canonicalization steps to support this paragraph
	These transformation steps are always defined as a pair which we call a canonicalization-step.
	Each canonicalization-step in our implementation consists of a canonicalization function and a de-canonicalization function.
	The canonicalization-steps are ordered as to not interfere with each other.
	More on that is discussed in section \ref{sec:ordering}.
	During the canonicalization process every canonicalization function is applied iteratively in this predefined order.
	% TODO: talk about why we need the reverse order
	For de-canonicalization, the de-canonicalization functions are applied in the reverse order in which the canonicalization steps are specified.
	It is also possible to pass information between the pairs of canonicalization and de-canonicalization functions of each step if required.
	This enables the support for more complex transformations.

	Due to the implementation of Minotaur and how we integrated our extension all the de-canonicalization could be done by updating meta data already required by minotaur during the canonicalization instead of relying on the explicit de-canonicalization.

	Our modified Minotaur version is available on GitHub \footnote{\href{https://github.com/KiSchulz/minotaur}{Extended Minotaur Version}}.

	\subsection{Canonicalization Steps \label{sec:steps}}
	% TODO: explain why we can limit our reasoning to a function for correctness instead of having to reason over the hole code snippet
	% TODO: explain what the depth of function is maybe just cite the original paper for that "as defined by cite..."
	In the following each canonicalization-step is described.
	They were selected such that each step maintains semantical equivalence, reduces the size of the key space and that it does not modify the code snippets depth.
	Here two code snippets are considered equivalent if they compute the same value and have the same effects on memory, including ordering of changes during execution, when using the same arguments.
	These three properties are shown for each step.
	%The depth is kept constant as increasing this has a large impact on runtime as shown in original paper \cite{liu24:minotaur}.

	% TODO: consider reducing the length of this paragraph by focusing only on why these properties where chosen and leave the rest for future work
	It might be possible to relax the correctness property to, for instance, allow the reordering of memory operations depending on the memory model.
	Similarly, the requirement of reducing the size of the key space could be relaxed such that it only holds over all steps but not for every individual step.
	Also, the depth constraint is not strictly required and could be dropped, but this would likely result in more complex  solver queries which could drastically impact the overall runtime of Minotaur and offset any benefit gained from using canonicalization.
	This link between depth and runtime was already explored in the original paper \cite{liu24:minotaur}.
	
	An example of all the steps applied sequentially to an example input is shown in figure \ref{fig:canon_full}

	\paragraph{Eliminating Unused Function Arguments}
	% explanation
	Some of the functions extracted by Minotaur have unused arguments which can be removed during canonicalization.
	% reduced key space
	By removing those the number of functions with the same body but different signatures are reduced.
	Thereby reducing the size of the key space.
	% correctness
	Let $f: T_1 \times ... \times T_n \to R$ be an extracted function where argument $t_i$ does not appear in the body of $f$.
	We can then define $g: T_1 \times ... \times T_{i-1} \times T_{i+1} \times ... \times T_n \to R$ where
	\[
		\forall t_1 \in T_1, ..., t_n \in T_n: f(t_1, ..., t_n) = g(t_1, ..., t_{i-1}, t_{i+1}, ..., t_n)
	\]
	This equality holds because $t_i$ does not affect the computation in $f$'s body.
	Setting the canonicalization $f' := g$, we obtain the same result for all valid inputs.
	% de-canonicalization
	As shown in figure \ref{fig:kv} the rewrite does not have an explicit function signature.
	Therefore no de-canonicalization is required.
	% depth
	Modifying the function signature has no impact on the depth of the given code snippet.

	\paragraph{Sorting of Function Arguments}
	% explanation
	Another modification that is done to the function signature is that the function arguments are sorted.
	The arguments are sorted by their type-name and internally each set of arguments of the same type is sorted by when they are used inside the function body.
	% reduced key space
	This defines a total order of function arguments for each function body and reduces the size of the key space.
	%correctness

	Let $f: T_1 \times ... \times T_n \to R$ be an input function and $f'$ the output function with reordered parameters according to permutation $\rho: [n] \to [n]$.
    Both functions accept the same set of arguments, just in different positions.
    For any input tuple $(t_1, ..., t_n)$, the function body computes the same result regardless of parameter order because the body operates on argument values, not their positional indices:
    \[
        f(t_1, ..., t_n) = f'(t_{\rho^{-1}(1)}, ..., t_{\rho^{-1}(n)}) = \text{body}(t_1, ..., t_n)
    \]
    Thus parameter reordering does not affect semantic equivalence.
	% de-canonicalization
	Because Minotaur maintains a mapping between the extracted functions arguments and the original code the snippet was extracted from, we can simply update this mapping and do not require explicit de-canonicalization.
	% depth
	Since only the function signature is modified there is no change to the depth.

	\paragraph{Renaming of Function Arguments}
	% explanation
	After the previous two transformations the signature is almost unique for each function body with the exception of the naming.
	To resolve this each argument is renamed depending on its position in the signature.
	% reduced key space
	Because now the names of all function arguments are defined by their position all functions with a given signature and body map to the same key.
	% correctness
	Given a function $f(t_1, ..., t_n) := g(t_1, ..., t_n)$ as the input to the transformation step and a function $f'(x_1, ..., x_n) := g(x_1, ..., x_n)$ as the output.
	If we apply $f$ and $f'$ to the same set of arguments $v_i, i \in [n]$ we get
	\[
		f(v_1, ..., v_n) = g(v_1, ...,v_n) = f'(v_1, ..., v_n)
	\]
	This shows that renaming the arguments does not change the result of the function.
	% de-canonicalization
	As mentioned previously, Minotaur maintains a mapping between the arguments of the extracted function and the original code snippet from which it was derived.
	This mapping does not rely on names but instead uses references to objects that possess names, eliminating the need for de-canonicalization.	
	% depth
	Renaming does not impact the depth of the function.
	
	\paragraph{Replacing Greater-Than with Less-Than}
	% explanation
	Comparison operations often have multiple semantically equivalent ways of being expressed.
	To address this every greater-than or greater-equal comparison is replaced with a less-than or less-equal comparison respectively and the operands are swapped.
	% reduced key space
	This reduces the size of the key space since now only less-than and less-equal comparisons are possible.
	% correctness
	The correctness of the transformation follows from the "lemma" below.
	\begin{align*}
		\forall x \forall y . (x\ P\ y \iff y\ P'\ x) \\
		with (P, P') \in {(>, <), (\geq, \leq)}
	\end{align*}
	% de-canonicalization
	For this transformation no de-canonicalization is needed.
	% depth
	The depth is not impacted, since only the predicate of a comparison operator is modified.

	\paragraph{Non-strict Operator Replacement}
	% explanation
	This transformation replaces non-strict comparison operators with strict ones whenever possible, subject to certain constraints.
	% depth
	The replacement is applied only when the comparison involves constant operands, ensuring that the depth remains unchanged and that no additional operations are introduced.
	% reduced key space
	By reducing the number of distinct ways to express equivalent comparisons, this transformation shrinks the key space.
	%correctness
	Each value of LLVM's built-in integral and floating-point types represents a specific real number, with the exception of the special values $NaN$ and $\pm \inf$.
	The real numbers form a total order; consequently, the set of all non-special values of each type also forms a total order.
	For floating-point types, this order can be extended by defining $- \inf$ as the minimum element and $+ \inf$ as the maximum element.
	Within a total order each value, with the exception of the minimum and maximum, have a greater and smaller neighbor.

	In a total order, every value except for the minimum and maximum has both an immediate predecessor and an immediate successor.
	The minimum only has a successor, and the maximum only has a predecessor.
	Due to this property, non-strict comparison operators can be replaced by strict ones by appropriately adjusting a constant operand, provided that a suitable neighboring value exists.

	For example, given an expression of the form $x \leq c$ where $x$ is a variable and $c$ is a constant, the expression can be transformed into $x < c + \epsilon(c)$ where $\epsilon(c)$ is the smallest representable increment at $c$ (e.g., $1$ for integers).
	Formally:
	\[
		\forall x . (x \leq c \iff x < c + \epsilon(c))
	\]
	Similar arguments apply for $\geq$ and for cases where the constant appears on the left-hand side of the comparison.
	% de-canonicalization
	No de-canonicalization is required for this transformation.

	\subsection{Ordering of the Canonicalization Steps \label{sec:ordering}}
	% Describe the order in which the steps are applied and explain why
	% first greater... to less... change then argument ordering then argument renaming

	It is important to order the canonicalization-steps such that they do not interfere with previous ones.
	In our case this is still relatively simple since we only have two constraints.

	First, the argument renaming step should be run after the last modification to functions arguments.
	In our case this implies that it has to run after the elimination of unused arguments step and after the argument sorting step.

	Second, the sorting of function arguments has to take place after the last modification to the function body in which the usage order of the arguments is changed.
	This means concretely that it has to be run after the step replacing greater than with less than operators.

	Based on those two constraints we can define the following order:

	\begin{enumerate}[noitemsep, topsep=0pt, leftmargin=*]
		\item Elimination of unused Function Arguments
		\item Replacing Greater-Than with Less-Than
		\item Non-strict Operator Replacement
		\item Sorting of Function Arguments
		\item Renaming of Function Arguments
	\end{enumerate}

	\subsection{Results}
	% Evaluation results
	% just the results no interpretation

	Building libgmp using our augmented version of Minotaur showed a speedup of 1.31x compared to regular Minotaur.
	This can also be seen in the bottom graph of figure \ref{fig:cache} which is why the orange plots stop earlier.
	In this graph it can also be seen that the respective curves have a similar shape but are shifted on the time axis.
	Overall, our canonicalizations only added 5.68 seconds of total CPU time for the build of libgmp.

	The overall cache size using our augmented version was only 78.3\% of the cache size of regular Minotaur which was 17734 key value pairs.
	When looking at figure \ref{fig:cache} it can be seen that the overall number of queries was quite similar.
	In comparison, the number of cache hits for our augmented version was 12.7\% higher and lead to 67.7\% cache hit rate, while regular Minotaur only achieved 59.2\%.
	This is also reflected in the 28.6\% higher number of solver invocations by regular Minotaur.
	When it takes to long to find a beneficial rewrite it times out.
	Our extended version shows a slightly lower number of timeouts relative to the total number of solver invocations of 25.1\% compared to 27.2\% compared to regular Minotaur.
	When looking at queries that were a cache hit where the cached key also has a solution associated with it, which is denoted as $sol$ in figure \ref{fig:cache}, we can see that this increased by 50\% for our solution.
	% TODO: consider using % time faster not speedup doe to the sentence structure
	Importantly, similar improvements were also measured in the total CPU time it took to build libgmp, where a speedup of 1.37x was observed.

	\section{Discussion}
	% Key findings
	% interpretation/explanation of the results

	The speedup measured by our extension is caused by the increase in the cache hit rate which leads to fewer long running solver invocations, fulfilling the main goal of our proposed solution.
	This was achieved even though only very simple transformations were applied.

	The different number of queries, which can be observed in figure \ref{fig:cache}, are also present between two runs of regular Minotaur.
	It is not clear if this is caused by LLVM producing different LLVM IR between runs or if it is caused by Minotaur.

	That the tests of libgmp pass indicates, that our canonicalization step maintains the sematics of the keys, therefore being correct.
